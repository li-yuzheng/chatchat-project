## 3. P0-1：BM25 索引缓存

### 问题

`server/file_rag/retrievers/ensemble.py:22-45`：

```python
@staticmethod
def from_vectorstore(vectorstore, top_k, score_threshold):
    faiss_retriever = vectorstore.as_retriever(...)
    docs = list(vectorstore.docstore._dict.values())          # ① 全库 chunk 取出来
    bm25_retriever = BM25Retriever.from_documents(             # ② 每次重新分词 + 建索引
        docs, preprocess_func=jieba.lcut_for_search,
    )
    return EnsembleRetrieverService(retriever=EnsembleRetriever(...))
```

每次检索都执行 ①②，成本 O(N × 平均长度)，N 是 chunk 数，**且不缓存**。

### 改法

新建 `server/file_rag/retrievers/bm25_cache.py`：

```python
"""按知识库版本缓存 BM25 索引，避免每次查询重建。"""
import threading
from collections import OrderedDict

from langchain_community.retrievers import BM25Retriever

_lock = threading.RLock()
_cache: "OrderedDict[tuple, tuple]" = OrderedDict()   # key -> (fingerprint, retriever)
MAX_ENTRIES = 4


def _fingerprint(vectorstore) -> tuple:
    """用文档数和内容哈希判断库有没有变，变了就重建。"""
    docs = list(vectorstore.docstore._dict.values())
    return (len(docs), hash(tuple(d.page_content[:64] for d in docs)))


def get_bm25(vectorstore, kb_key: str, top_k: int, preprocess_func):
    docs = list(vectorstore.docstore._dict.values())
    fp = (len(docs), hash(tuple(d.page_content[:64] for d in docs)))

    with _lock:
        hit = _cache.get(kb_key)
        if hit and hit[0] == fp:
            _cache.move_to_end(kb_key)
            retriever = hit[1]
        else:
            retriever = BM25Retriever.from_documents(docs, preprocess_func=preprocess_func)
            _cache[kb_key] = (fp, retriever)
            _cache.move_to_end(kb_key)
            while len(_cache) > MAX_ENTRIES:
                _cache.popitem(last=False)
    retriever.k = top_k          # k 是查询级参数，不进缓存
    return retriever
```

然后 `ensemble.py` 里改成调用它，`kb_key` 用 `f"{kb_name}/{vector_name}"` 传进来
（需要给 `from_vectorstore` 加一个可选参数，或在 `FaissKBService.do_search` 里预置）。

### 验证（关键，必须做）

写 `bench/bench_retrieval.py`：同一批 20 个 query，各跑 5 次，统计
`do_search` 的 P50 / P95，改前改后对比；再用测试集确认 Recall@3 不变（缓存不该改变结果）。

**预期**：小库（几千 chunk）能省 20~60ms；chunk 上万时省几百毫秒。

### 4.2 评估脚本

`bench/eval_rag.py`，两层指标：

```python
# 检索层
def recall_at_k(gold_files, retrieved_docs, k):
    hit = {d.metadata["source"] for d in retrieved_docs[:k]} & set(gold_files)
    return 1.0 if hit else 0.0

def mrr(gold_files, retrieved_docs):
    for i, d in enumerate(retrieved_docs, 1):
        if d.metadata["source"] in gold_files:
            return 1.0 / i
    return 0.0

# 生成层：看答案里是否包含关键实体 / 是否在"应拒答"题目上胡说
```

## 5. P1-1：分阶段耗时埋点

在 `kb_chat.py` 里加一个轻量的计时上下文（不要引 OpenTelemetry，太重）：

```python
import time, contextlib

@contextlib.contextmanager
def stage(name: str, sink: dict):
    t = time.perf_counter()
    try:
        yield
    finally:
        sink[name] = round((time.perf_counter() - t) * 1000, 1)
```

然后在 `kb_chat` 里：

```python
timing = {}
with stage("retrieve", timing):
    docs = await run_in_threadpool(search_docs, ...)
with stage("prompt", timing):
    ...
# 首帧里把 timing 带上，前端可展示，日志可统计
```

有了这个，你才能回答"延迟卡在哪一段"——这也是面试官最爱追问的。

## 6. P1-2：reranker 可开关

### 6.1 补配置

`settings.py` 的 `KBSettings` 里加：

```python
USE_RERANKER: bool = False
"""是否启用重排（需要额外的 rerank 模型）"""
RERANKER_MODEL: str = "bge-reranker-base"
RERANKER_MAX_LENGTH: int = 512
RECALL_TOP_K: int = 20
"""粗排召回数，重排后会截断到 top_k"""
```

### 6.2 打开被注释的代码

`kb_chat.py:148-162` 已有完整实现，只是被注释。改写为：

```python
if Settings.kb_settings.USE_RERANKER:
    from chatchat.server.reranker.reranker import LangchainReranker
    reranker = LangchainReranker(top_n=top_k, model_name_or_path=..., max_length=...)
    docs = reranker.compress_documents(documents=docs, query=query)
```

### 6.3 关键设计：两阶段检索

`recall_top_k=20` 粗排 → 重排 → `top_k=3` 给模型。
不要拿 20 条全部塞给 LLM（token 多、噪声大）。

**验证**：评估脚本里对比开/关 reranker 的 Recall@3 和 MRR，以及延迟变化。
这才是"用延迟换精度"的量化表达。

## 7. P2：其他

**向量库缓存数**
`CACHED_VS_NUM` 从 1 调到 3，并在 `startup` 里加预热（启动时加载最近访问的库）。
验证：多库交替查询的 P95。

**Docker**
写 `Dockerfile` + `docker-compose.yml`（API + Ollama），`HEALTHCHECK` 打 `/docs`。
这是"能部署"的证据。

**CI**
GitHub Actions：`pip install` → `pytest tests/`（含冒烟测试）→ `ruff`。
桩 LLM 让测试不需要任何 Key，天然适合 CI。

**`/v1/models` 应与本地配置取并集（P3，但很好讲）**
现在 `openai_routes.py:121-131` 是把请求直接转发给上游 `client.models.list()`，
完全不读本地 `model_settings.yaml`。后果有两个：

1. 上游 `deepseek-chat` 这种别名不返回，但本地配了也能用 —— 接口「漏报」；
2. 上游返回了本地没配的模型，用户在下拉框里选了却调用失败 —— 接口「虚报」。

改法：`configured | upstream` 取并集，并给每项标注 `source: config|upstream`。
顺便可以暴露 `/v1/models?source=config` 只返回本地可用的。

这在面试里是个很好的「你发现过什么设计问题」的素材，成本只有十几行。
