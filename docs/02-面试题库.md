# 面试题库：把 Langchain-Chatchat 讲成你的项目

> 用法：`★` 是必答题（一定问），`★★` 是区分度题（答得好直接拉开差距）。
> 每题给的是**答题骨架**，不是让你背原文。面试时说 3~5 句，然后停下来等追问。

---

## 一、开场：这个项目怎么讲（60 秒版本）

**★ Q1：介绍一下你这个项目。**

> 我做的是一个企业知识库问答系统，基于 Langchain-Chatchat 二次开发。
> 它解决的问题是：公司内部文档散落在各种 PDF、Word、Excel 里，员工想查东西只能靠搜索，
> 而通用大模型又答不出内部信息。
>
> 我的工作分三块：
> **一是把架构吃透并做了性能优化**——比如我发现它的混合检索每次查询都要重建 BM25 索引，
> 文档量上来以后检索延迟线性增长，我改成按文档版本缓存，P95 从 X ms 降到 Y ms；
> **二是扩展了模型接入层**——原来只支持本地模型，我接入了 DeepSeek 云端模型，
> 并且把密钥从明文配置改成环境变量注入；
> **三是补了工程化**——离线桩服务、RAG 全链路冒烟测试，让改动有回归保护。
>
> 技术上它是 FastAPI + Streamlit + LangChain + FAISS，向量库、模型平台、检索策略
> 都做成了可插拔的。

**★ Q2：为什么选这个项目？/ 这个项目有什么技术难点？**

难点三选一，按你实际做过的说：
1. **流式 + 状态的编排**：检索是同步阻塞的，生成是异步流式的，要在一个 HTTP 请求里
   既保证不阻塞事件循环，又要边生成边推送。
2. **多后端抽象**：7 种向量库、6 种模型平台、3 种检索策略，要做到加一个后端不改业务代码。
3. **RAG 效果与延迟的权衡**：检索多了准但慢，少了快但答不准。

**★★ Q3：你自己做了什么？哪些是原来就有的？**

> 这段一定要分清，否则会被认为"拿开源项目充数"。
> 框架是开源的；我的增量是：性能分析与优化、多模型接入与密钥治理、
> 测试与可观测性、以及若干 bug 修复（非流式不带引用、工厂死代码）。

## 二、架构与设计

**★ Q4：整体架构分几层？**

接口层（FastAPI 路由）→ 业务层（RAG 编排、Agent）→ 能力层（知识库、检索、模型）
→ 基础设施层（配置、DB、外部服务）。
接口层只做参数搬运，业务层不关心用哪个向量库，能力层通过抽象类和工厂解耦。

**★ Q5：为什么用 Streamlit 而不是前后端分离？**

原项目定位是"开箱即用的本地应用"，Streamlit 用 Python 写页面、无需构建工具，
部署简单（单进程）。
代价是：**页面每次交互整个脚本重跑一遍**，状态要靠 `st.session_state` 手动维护，
复杂交互很别扭，长连接和并发能力也弱。
如果要做成生产系统，我会拆成 React/Vue + 独立 API。

**★★ Q6：项目里有哪些设计模式？**

| 模式 | 位置 | 作用 |
|---|---|---|
| 模板方法 | `KBService.search_docs` → `do_search` | 通用流程放基类，差异留给子类 |
| 工厂 | `KBServiceFactory.get_service` | 按 `vs_type` 造不同向量库实例 |
| 策略 | `file_rag/retrievers`（vectorstore/ensemble） | 检索算法可替换 |
| 适配器 | `LocalAIEmbeddings` 等 | 统一不同厂商的嵌入接口 |
| 单例 + 对象池 | `kb_faiss_pool` | 向量库只加载一次，LRU 淘汰 |

**★★ Q7：加一个新的向量库要改哪些地方？**

1. 在 `SupportedVSType`（`kb_service/base.py:47`）加枚举
2. 写一个类继承 `KBService`，实现 5 个 `do_*` 方法
3. 在 `KBServiceFactory.get_service` 加一个分支

业务层完全不用动——这就是模板方法 + 工厂的价值。

**★ Q8：两个进程怎么通信？**

`chatchat start -a` 起两个独立进程（API 用 uvicorn，WebUI 用 streamlit bootstrap），
**没有直接通信**，全部走 HTTP。用 `mp.Manager().Event()` 做启动顺序同步：
API 的 lifespan 里 `set()`，主进程 `wait()` 到才起 WebUI。

**★ Q9：配置怎么管理？**

pydantic-settings + 4 个 YAML（basic / model / kb / prompt），按 `CHATCHAT_ROOT` 定位。
好处是类型校验、IDE 补全、可回写（`chatchat init` 生成带注释的模板）。
有个坑：它按文件 mtime 做缓存，改了配置可能不生效，要重启。

## 三、RAG 原理

**★ Q10：完整讲一下 RAG 的流程。**

离线：文档 → 按扩展名选 loader 解析 → 切分（chunk_size=750, overlap=150）→
embedding 向量化 → 写入向量库 + 元数据库登记。

在线：用户提问 → 向量化 → 检索 top_k → （可选重排）→ 拼进 prompt 模板 →
调 LLM 生成 → 流式返回 + 附带引用。

**★★ Q11：为什么要切分？chunk_size 怎么定？**

模型上下文有限，且检索粒度要匹配问题粒度：切太大则噪声多、向量语义被稀释；
切太小则语义不完整。750 字符 + 150 重叠是中文经验值，重叠是为了避免答案被切断在边界。
实际要按文档类型调：FAQ 可以小，技术文档要大。

**★★ Q12：为什么用混合检索（向量 + BM25）？**

向量检索擅长语义泛化（"怎么退款"能匹配"退货流程"），但对**专有名词、型号、错误码**
这类精确词不敏感；BM25 正好相反。
两者用 `EnsembleRetriever(weights=[0.5,0.5])` 融合，互补。
代价是要维护两套索引，且 BM25 要中文分词（用 jieba）。

**★ Q13：score_threshold 是什么？**

过滤低相关结果。但要注意这个项目里它其实**不是相似度**——
FAISS 用的是 L2 距离，值越小越相关，所以默认给到了 2.0；
而接口注释写"取值 0-1，越小越相关"，是矛盾的（`kb_chat.py:34`）。这是代码里一个真实坑。

**★★ Q14：检索不准怎么排查？**

按链路逐段定位，不要一上来就换模型：
1. **看 chunk**：检索到的片段本身是否包含答案？不含 → 切分或解析有问题（PDF 表格解析失败很常见）
2. **看召回**：答案所在片段有没有被召回？没有 → 提高 top_k / 加混合检索 / 换 embedding
3. **看排序**：召回了但排在后面 → 加 reranker
4. **看生成**：上下文对但答错 → prompt 模板 / 模型能力问题

**★★ Q15：怎么评估 RAG 效果？**

不能靠"感觉答得不错"。要有测试集：50~100 条「问题 → 标准答案 → 出处」。
分两层指标：
- **检索层**：Recall@k（前 k 个片段里有没有含答案的）、MRR（正确片段排多前）
- **生成层**：答案准确率、引用正确率、幻觉率（答案里的陈述能否在上下文中找到依据）

检索和生成要分开评，否则出了问题不知道改哪。

**★ Q16：为什么换 embedding 模型必须重建向量库？**

不同模型的向量空间维度、语义分布都不同，混在一起检索等于拿两种坐标系的点算距离，
结果没有意义。所以要整库重算（`chatchat kb -r`）。

**★★ Q17：什么时候该用微调而不是 RAG？**

RAG 解决"知识"问题（事实、文档），微调解决"能力/风格"问题（格式、语气、领域推理）。
知识频繁变 → RAG；知识稳定但要改变输出形式 → 微调。两者可以叠加。

## 四、工程实现（结合本项目）

**★ Q18：流式输出怎么实现的？**

三层配合：
1. LLM 侧：`ChatOpenAI(streaming=True)`，LangChain 通过 callback 逐 token 回调
2. 进程内：`AsyncIteratorCallbackHandler` 内部是 `asyncio.Queue`，
   `callback.aiter()` 持续取；`wrap_done()` 保证结束/异常时能退出
3. HTTP 侧：`EventSourceResponse` 把生成器包装成 SSE，每帧一个 `chat.completion.chunk`

**★★ Q19：为什么要 `run_in_threadpool`？**

`async def` 里一旦调用同步阻塞函数（FAISS 检索、BM25 分词），整个事件循环被占住，
所有并发请求一起卡。
`kb_chat.py:79` 把 `search_docs` 丢到线程池，`await` 期间事件循环可以去处理别的请求。
这是 asyncio 的经典坑：**异步框架里混同步 IO，比不用异步还糟**。

**★★ Q20：多平台同名模型怎么负载均衡？**

`openai_routes.py:33`：按 `(模型名, 平台)` 建 `asyncio.Semaphore`，并发上限来自
配置的 `api_concurrencies`。
选平台逻辑：优先选还有空闲配额的，否则选当前占用最少的。等于一个简易的加权最少连接。

**★ Q21：向量库怎么保证线程安全？**

`kb_faiss_pool` 里每个库包一层 `ThreadSafeFaiss`：
- `RLock` 保证同一库的读写互斥
- `threading.Event` 解决**加载中**的竞态——后到的请求 `wait_for_loading()` 等前一个加载完，
  避免同一个库被加载两次

**★★ Q22：为什么要做对象池 / 缓存？**

`FAISS.load_local` 要读盘 + 反序列化，几百 MB 的库要几秒。
请求来了才加载肯定不行，所以要常驻内存并复用。
但内存有限，所以用 LRU 淘汰（`OrderedDict` + `popitem(last=False)`）。

**★ Q23：你的测试怎么写的？**

`tests/test_rag_pipeline.py` 做全链路冒烟：
进程内起一个 OpenAI 兼容的桩 LLM（`tools/mock_llm_server.py`），
真实跑 `kb_chat → 检索 → 拼 prompt → 调模型 → 返回`，断言回答里包含检索到的上下文。
好处：**不依赖云厂商 Key、不花钱、秒级反馈**，改完代码跑一下就知有没有破坏主链路。

**★ Q24：密钥怎么管理的？**

原版是明文写在 `model_settings.yaml` 里，很容易跟着代码提交进 git。
我改成配置里写占位符 `${DEEPSEEK_API_KEY}`，加载时由 pydantic validator 从环境变量展开。
这样仓库里永远只有占位符，换机器只配环境变量。

## 五、性能与优化（最能体现深度）

**★★★ Q25：你做过什么性能优化？怎么定位的？**

> 这是全场最值钱的一题，按"发现问题 → 定位 → 量化 → 优化 → 验证"讲，不要只报结果。

**发现问题**：读 `retrievers/ensemble.py:37` 时注意到，`from_vectorstore()` 里
每次都执行 `BM25Retriever.from_documents(list(vectorstore.docstore._dict.values()))`。

**定位**：这条路径在每次检索都会走 ——
`do_search → get_Retriever("ensemble").from_vectorstore(...)`。
意思是**每个请求都把全库 chunk 取出来，用 jieba 重新分词，重建一次倒排索引**。

**量化**：加计时埋点（或 cProfile）测 `from_vectorstore` 的耗时，对比不同文档量。
N 个 chunk 时是 O(N) 分词 + O(N) 建索引，不走缓存，纯属重复劳动。

**优化**：把 BM25 索引按 `(kb_name, 文档指纹)` 缓存起来，文档增删时失效。
第一次查询建好，后续直接复用。可以进一步用 jieba 的 `lcut` 批量预处理 + 预计算词频。

**验证**：同样的查询跑 N 次，看 P50/P95 变化；同时用测试集确认召回率没有下降
（缓存不能改变检索结果，只是省时间）。

**★★ Q26：为什么向量库缓存默认只存 1 个？**

`CACHED_VS_NUM = 1`（`settings.py:164`）。这是**内存与延迟的权衡**：
每个库几百 MB，全常驻会 OOM；只存 1 个则多库场景频繁换入换出。
合理做法是按可用内存动态设定（比如 3~5 个）或做**预热**：启动时把热点库加载好。

**★★ Q27：为什么默认没开 reranker？开了会怎样？**

`kb_chat.py:148-162` 整段被注释掉了，说明作者试过但没启用。
原因是 reranker 是**本地交叉编码器模型**，要额外显存 + 每对 (query, doc) 都要过一遍模型，
延迟显著增加。
对我的 6GB 显卡来说，正确做法是：先粗排召回 top 20，再重排取 top 3，
用**可控的额外延迟换精度**，并且做成可配置开关。

**★★ Q28：如何降低首字延迟（TTFT）？**

用户体感主要取决于首字时间。可以：
1. 检索与 prompt 组装并行化（历史消息预处理提前做）
2. 小模型/便宜模型做 query 改写，避免长 prompt
3. 减少 top_k（token 越少越快）
4. 预热向量库与模型连接（避免首个请求冷启动）
5. 流式协议上，**先推引用再推 token**——这个项目就是这么做的，用户先看到"匹配到哪些文档"

**★ Q29：并发上来了怎么扩展？**

现状：单进程 uvicorn，向量库在**进程内存**里，多 worker 会各自加载一份（内存翻倍）。
可行路径：
1. 向量库外置（Milvus/PG），API 层变无状态，横向扩 worker
2. 嵌入/重排做成独立服务，避免每个 worker 各自加载模型
3. 检索结果加一层 Redis 缓存（相同 query 命中）
4. 流式请求占连接久，注意 uvicorn 的连接数上限和反向代理超时

## 六、故障排查（考应变）

**★ Q30：用户说"知识库明明有，却回答不知道"，怎么查？**

1. 看检索阶段：`/knowledge_base/search_docs` 直接查，看有没有召回
2. 没召回 → 查文件是否真的入库（`list_files`）、向量模型是否一致（换过模型没重建）
3. 召回了但答不知道 → 看 `score_threshold` 是否过滤太狠、prompt 模板是否把上下文丢了
4. 上下文有答案但模型答错 → 换模型或调 prompt（要求"必须基于给定信息回答"）

**★★ Q31：`/v1/models` 卡住 30 秒不返回，你怎么定位？**

这个项目里真实踩过：默认配置里有 `xinference`、`oneapi` 平台，指向不存在的本地服务，
`get_config_platforms()` 遍历时会去连，超时才返回，把整个接口拖死。
定位方法：`curl -w "%{time_total}"` 看耗时 → 打点看哪个平台慢 → 发现是根本没部署的平台。
解决：删掉无用平台配置，只留实际在用的。

**★★ Q32：白屏 / 报 `need to install PyArrow`？**

Streamlit 的自定义组件依赖 pyarrow，而 pyarrow 高版本要求 numpy≥2，
项目锁的是 numpy<1.25，装出来的版本组合自相矛盾。
正确组合：`pyarrow==15.0.2` + `numpy==1.24.4`。
**教训**：这类"依赖地狱"要用 `pip check` + 约束文件锁版本，不能靠 `pip install -U` 撞运气。

**★★ Q33：端口被占用 / 起不来？**

`Port 8501 is already in use` / `[Errno 10048]`。
说明上一个实例没退干净（streamlit 经常残留）。
我写了 `stop_all.py` 按端口查 PID 并结束，配合启动前自检，直接告诉用户占用进程的 PID。

## 七、追问链（面试官顺着往下问）

**★★ Q34：你说 BM25 索引缓存，文档更新时怎么保证一致性？**

用文档指纹做 key：`(kb_name, file_count, max(mtime), total_chunks)` 或哈希。
变更检测到不一致就重建；也可以用写时失效（add/delete 时主动把对应 key 置脏）。

**★★ Q35：缓存会不会导致内存泄漏？**

会，所以要设上限 + LRU。BM25 索引本身是词表 + 倒排链，通常比向量小一个量级，
但要限制库数量，并在库被删除时主动清理。

**★★ Q36：如果让你把检索准确率提升 20%，你会怎么做？**

按投入产出排优先级：
1. 先修数据侧：解析质量（PDF 表格/图片）、切分策略——通常收益最大
2. 加 reranker
3. query 改写 / 多查询（HyDE、多路召回融合 RRF）
4. 元数据过滤（按文档类型/时间）
5. 最后才是换更大的 embedding 模型

**★★ Q37：怎么防止模型胡编（幻觉）？**

三层：
1. prompt 约束（明确"资料里没有就说不知道"，本项目 `rag.default` 模板就是这么写的）
2. 强制引用：要求答案带 `[1][2]` 编号，前端可点击溯源
3. 后置校验：检查答案的关键实体是否出现在上下文中（可以做但要控制误伤）

**★ Q38：这个项目有什么不足？**

主动说，且要带改法：
1. 只支持单机，向量库在进程内存，不能水平扩展
2. 没有 RAG 评估体系，优化全靠感觉
3. 非流式接口不返回引用，前后端契约不一致
4. 配置明文存密钥（已改）、`start -a` 不好调试（已拆）

## 八、如果你要加的功能（考设计能力）

**★★ Q39：怎么接入公司已有的用户体系做权限隔离？**

最小改动方案：
1. FastAPI 加依赖注入中间件，解析 JWT 拿 `user_id/tenant_id`
2. 知识库表加 `owner_id`、`visibility`；`KBServiceFactory.get_service_by_name` 前先校验归属
3. 检索层再加一层兜底：**在 metadata 上做过滤**，防止越权召回
4. 引用里的下载链接改成带签名的临时 URL（本项目 `/knowledge_base/download_doc` 目前是裸的）

**★★ Q40：怎么支持多轮对话里的指代（"它"指什么）？**

现在的做法是直接把历史消息塞进 messages，问题里的"它"模型可能猜错。
更好的做法是**检索前做 query 改写**：用一次小模型调用把
"它的价格呢" → "iPhone 15 的价格是多少"，再拿改写后的 query 去检索。
代价是多一次 LLM 调用，可以用缓存 + 小模型控制成本。

**★★ Q41：怎么支持增量更新文档？**

现在 `chatchat kb -i` 是扫描本地目录新文件。
生产上要：文件监听（或对象存储事件）→ 计算内容哈希 → 变了就删旧 chunk 再插新的
→ 更新 BM25 缓存 key。注意删 chunk 要按元数据里的 `file_id` 批量删。

## 九、最后：反问环节
