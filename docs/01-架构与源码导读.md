## 1. 一句话定位

一个**把本地/云端大模型接到私有知识库上**的 RAG 应用：文档入库 → 切分 → 向量化 →
检索 → 拼提示词 → 调模型 → 流式返回并附带引用。对外同时提供**原生接口**和
**OpenAI 兼容接口**，自带 Streamlit 前端和 Agent（工具调用）能力。

技术栈：FastAPI + Uvicorn（API）、Streamlit（WebUI）、LangChain 0.1.17（编排）、
FAISS/Milvus/Chroma/ES/PG（向量库，可插拔）、SQLAlchemy + SQLite（元数据）、
pydantic-settings + YAML（配置）。

代码量：128 个 .py，核心在 `chatchat/server/`。

## 3. 进程模型：为什么 `chatchat start -a` 不好调试

`startup.py:209 start_main_server()`：

- `mp.set_start_method("spawn")`（`startup.py:246`）
- 起两个 `Process`：`run_api_server`（`startup.py:41`）和 `run_webui`（`startup.py:73`）
- 用 `mp.Manager().Event()` 做启动同步：API 起来了才起 WebUI（`startup.py:295`、`300`）

API 进程里是 `uvicorn.run(app)`（`startup.py:70`）；
WebUI 进程里不是起独立服务，而是 `streamlit.web.bootstrap.run(webui.py)`（`startup.py:172`），
这就是为什么 WebUI 的配置项要手写成一长串 `flag_options`（`startup.py:88-149`）。

> 面试可讲：**spawn 模式下子进程重新 import 一遍模块**，所以断点打不进业务代码；
> 我们把它拆成 `run_api.py` / `run_webui.py` 两个单进程入口才可调试。

## 4. 配置体系（读代码前必须知道）

`Settings` 是 pydantic-settings 的聚合对象，4 个子配置各对应一个 YAML，放在
`CHATCHAT_ROOT`（本项目 `D:\chatchat-data`）：

| 配置类 | 文件 | 管什么 |
|---|---|---|
| `BasicSettings` | `basic_settings.yaml` | 端口、路径、跨域、代理 |
| `ApiModelSettings`（`settings.py:329`） | `model_settings.yaml` | 默认模型、`MODEL_PLATFORMS` |
| `KBSettings`（`settings.py:153`） | `kb_settings.yaml` | 切分大小、top_k、`CACHED_VS_NUM` |
| prompt 模板 | `prompt_settings.yaml` | `rag.default` 等 Jinja2 模板 |

两个容易踩的点：

1. **`Settings` 带文件 mtime 缓存**。`pydantic_settings_file.py:243 _cached_settings()`
   会按文件 mtime 判断是否 `settings.__init__()` 重新加载。所以运行时改内存里的配置，
   下一次访问属性可能就被文件内容冲掉——写测试时要先 `auto_reload = False`
   （`pydantic_settings_file.py:186`）。
2. **密钥原本是明文存在 YAML 里**。这是我们本次改造点之一，见第 11 节。

## 5. 主链路：一次 RAG 问答发生了什么

这是必须能**背着讲出来**的一条链。以 `POST /chat/kb_chat` 为例。

### 5.1 入口

`server/api_server/chat_routes.py:41`

```python
chat_router.post("/kb_chat", summary="知识库对话")(kb_chat)
```

直接把 `kb_chat` 函数当路由处理函数注册——参数全靠 FastAPI 的 `Body(...)` 注解
（`server/chat/kb_chat.py:30-62`），所以函数签名本身就是 API 文档。

### 5.2 前置校验（同步部分，在返回 SSE 之前）

```python
if mode == "local_kb":                       # kb_chat.py:63
    kb = KBServiceFactory.get_service_by_name(kb_name)
    if kb is None:
        return BaseResponse(code=404, msg=f"未找到知识库 {kb_name}")
```

注意：这是**唯一**可能返回 JSON 错误的地方；进入迭代器之后的异常都会变成 SSE 里的 error 事件。

### 5.3 生成器内部（真正的 RAG）

`knowledge_base_chat_iterator()`（`kb_chat.py:68`）逐步：

| 步骤 | 代码 | 说明 |
|---|---|---|
| 1. 历史转对象 | `kb_chat.py:72` | `History.from_data(h)` |
| 2. 取 KB 实例 | `kb_chat.py:75` | 工厂按库名查 DB 得到 vs_type/embed_model |
| 3. 校验嵌入模型可用 | `kb_chat.py:76` `kb.check_embed_model()` | 会真的发一次 embedding 请求 |
| 4. 检索 | `kb_chat.py:79` `run_in_threadpool(search_docs, ...)` | **同步阻塞操作丢到线程池**，避免卡死事件循环 |
| 5. 拼引用 | `kb_chat.py:86` `format_reference(...)` | 生成 `[1] [文件名](链接)` 形式的引用块 |
| 6. 直接返回模式 | `kb_chat.py:113` | `return_direct=True` 时不调 LLM，只回检索结果 |
| 7. 建回调 | `kb_chat.py:125` | `AsyncIteratorCallbackHandler` 是流式的关键 |
| 8. 建模型 | `kb_chat.py:142` `get_ChatOpenAI(...)` | 按 model 名反查平台配置 |
| 9. 拼上下文 | `kb_chat.py:163` | `"\n\n".join(doc["page_content"])` |
| 10. 选模板 | `kb_chat.py:165-167` | 没检索到就切到 `rag.empty` 模板 |
| 11. 组 Prompt | `kb_chat.py:168-170` | 历史消息 + 本轮（含 context/question 变量） |
| 12. 组链 | `kb_chat.py:172` `chain = chat_prompt \| llm` | LangChain 的管道语法 |
| 13. 后台跑 | `kb_chat.py:175` `create_task(wrap_done(chain.ainvoke(...), callback.done))` | 边跑边通过 callback 吐 token |
| 14. 先发引用 | `kb_chat.py:183-193` | **流式第一帧带 docs**，前端据此渲染"知识库匹配结果" |
| 15. 再发 token | `kb_chat.py:195-203` | 每个 token 一帧 `chat.completion.chunk` |

### 5.5 三个必须知道的实现细节

**(1) 为什么要 `run_in_threadpool`**
`search_docs` 里是同步的 FAISS/BM25 调用，直接在 `async def` 里跑会阻塞整个事件循环，
所有并发请求一起卡住。所以 `kb_chat.py:79`、`91`、`98` 都包了一层。

**(2) 流式为什么能"边生成边发"**
`AsyncIteratorCallbackHandler`（LangChain 提供）内部是一个 `asyncio.Queue`：
LLM 每吐一个 token 就 `put` 进队列，`callback.aiter()` 从队列里持续 `get`。
`wrap_done()`（`server/utils.py:468` 附近）包一层，正常结束或异常都会 `event.set()`，
让 `aiter()` 能退出。

**(3) 非流式分支有 bug，面试可以主动提**
`kb_chat.py:204-215`：`stream=False` 时返回的 `OpenAIChatOutput` **没有带 docs**，
而流式第一帧是带的。这是接口不一致——前端如果切非流式就拿不到引用。
我们写冒烟测试时就踩到了这个点。

## 6. 第二条链路：OpenAI 兼容入口怎么分发

现代前端（`webui_pages/kb_chat.py:199`）其实走的是这条：

```python
client = openai.Client(base_url=f"{api_url}/knowledge_base/local_kb/{selected_kb}", api_key="NONE")
```

也就是**把知识库名编进 base_url**，然后用标准 OpenAI SDK 调 `/chat/completions`。

对应实现：`server/api_server/kb_routes.py:35-66`

```python
@kb_router.post("/{mode}/{param}/chat/completions")
async def kb_chat_endpoint(mode, param, body: OpenAIChatInput, request):
    ...
    return await kb_chat(query=body.messages[-1]["content"], mode=mode, kb_name=param, ...)
```

`mode` 三选一：`local_kb`（本地库）/ `temp_kb`（临时文件库）/ `search_engine`（联网搜索）。
非标准参数（`top_k`、`prompt_name`、`return_direct`）走 `body.model_extra`
——因为 `OpenAIChatInput` 允许额外字段。

另一条 `/v1/chat/completions`（`chat_routes.py:45`）按请求体特征分发：

```
有 tool_choice + tool_input  → 直接执行工具，把结果塞进 prompt 再回答（chat_routes.py:94-155）
有 tools                     → 走 Agent 循环（chat_routes.py:158-188）
都没有                        → 纯 LLM 对话，转发到对应平台（chat_routes.py:189-210）
```

**并发控制**在 `openai_routes.py:33 get_model_client()`：按 `(模型, 平台)` 维度建
`asyncio.Semaphore(api_concurrencies)`，重名模型优先选空闲平台，否则选当前占用最少的。
这是个很值得讲的细节——**多平台同模型名的负载均衡**。

## 7. 知识库层：模板方法 + 工厂 + 缓存池

### 7.1 类结构

```
KBService (ABC)                    server/knowledge_base/kb_service/base.py:58
├── 模板方法（通用逻辑，调 do_*）
│   create_kb / clear_vs / add_doc / search_docs(:201) / update_doc ...
└── 抽象方法（子类实现）
    do_create_kb / do_search(:311) / do_add_doc(:323) / do_delete_doc / do_clear_vs

FaissKBService   faiss_kb_service.py      ← 默认
MilvusKBService / ZillizKBService / PGKBService
ESKBService / ChromaKBService / RelytKBService / DefaultKBService
```

`search_docs`（`base.py:201`）就是模板方法：先 `check_embed_model()`，再 `do_search()`。
子类只关心"怎么在自己这个向量库里搜"。

`KBServiceFactory`（`base.py:348`）两段式：

- `get_service(kb_name, vs_type, embed_model)`：按类型分支 `import` 对应实现（**延迟导入**，避免为了用 FAISS 却把 Milvus 依赖也拉起来）
- `get_service_by_name(kb_name)`：先查 DB 拿到该库的 `vs_type` / `embed_model`，再委托给上面

### 7.2 FAISS 实现与缓存

`faiss_kb_service.py:66 do_search()`：

```python
with self.load_vector_store().acquire() as vs:
    retriever = get_Retriever("ensemble").from_vectorstore(vs, top_k=top_k, score_threshold=score_threshold)
    return retriever.get_relevant_documents(query)
```

`load_vector_store()` → `kb_faiss_pool.load_vector_store(...)`（`faiss_cache.py:91`）。

缓存池设计（`kb_cache/base.py`）：

- `CachePool` 用 `OrderedDict` 做 **LRU**，`_check_count()` 超出就 `popitem(last=False)`（`base.py:73`）
- 每个缓存项是 `ThreadSafeFaiss`，继承 `ThreadSafeObject`：
  - `RLock` 保证同一向量库读写互斥（`base.py:34 acquire()`）
  - `threading.Event` 解决"**加载中**"的竞态：`get()` 会先 `wait_for_loading()`（`base.py:78`）
- 池容量 = `Settings.kb_settings.CACHED_VS_NUM`，**默认 1**（`settings.py:164`）

> 这是本项目最大的性能隐患之一：多知识库场景下，请求在 A/B 库之间切换会反复
> 从磁盘 `FAISS.load_local`。面试时主动指出 + 给出改造方案，是加分项。

### 7.3 检索器策略模式

`file_rag/retrievers/`：

| 实现 | 逻辑 |
|---|---|
| `vectorstore.py` | 纯向量检索，`similarity_score_threshold` |
| `ensemble.py` | **BM25（jieba 分词）+ 向量**，`EnsembleRetriever(weights=[0.5, 0.5])` |
| `milvus_vectorstore.py` | Milvus 专用 |

工厂在 `file_rag/utils.py:9`，靠字符串拿类。默认 FAISS 走 `ensemble`。

**重点（面试高频）**：`ensemble.py:37` 每次查询都执行

```python
docs = list(vectorstore.docstore._dict.values())
bm25_retriever = BM25Retriever.from_documents(docs, preprocess_func=jieba.lcut_for_search)
```

也就是**每个请求都把全库 chunk 拿出来重新分词、重建 BM25 索引**。
几千个 chunk 时这一句就是几十到几百毫秒，且随文档量线性增长。
正确做法是按 `(库, 文档版本)` 缓存 BM25 索引，文档变更时失效——这是我们要做的第一个优化。

## 10. 前端：Streamlit 如何消费 SSE

`webui_pages/utils.py`：

- `ApiRequest`（:25）：httpx 封装，`get/post/delete` 统一处理错误
- `_httpx_stream2generator`（:112）：把 `httpx` 的字节流逐行解析成 SSE 事件
- 各业务方法（`chat_chat`、`upload_kb_docs`…）只是拼参数

页面侧 `webui_pages/kb_chat.py:225`：

```python
for d in client.chat.completions.create(messages=..., model=..., stream=True, extra_body=extra_body):
    if first:                                  # 第一帧是检索结果

```

**这就是"第一帧带 docs"约定的消费端**——前后端靠这个约定对齐。
